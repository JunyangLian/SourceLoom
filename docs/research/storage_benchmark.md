# Task 07：存储与检索后端对照实验设计

> 目的：用同一批 chunk、同一批问句、同一套指标，比较现有 SQLite FTS5 方案与 Zvec / Tantivy / Qdrant / LanceDB 的真实差距。
> 原则：只记录本机实测；厂商博客数字（见 `zvec.md`）只作参考，不进入结论。

## 一、对照对象

| 后端 | 形态 | 全文检索 | 向量 | Windows 打包 | 本轮角色 |
| --- | --- | --- | --- | --- | --- |
| SQLite FTS5（现有） | Python 内置 | trigram / `instr` 兜底 | 自建 int8 矩阵 | 无额外依赖 | 基线 |
| Zvec | C++ 原生 + Python SDK | 原生 FTS + Jieba | HNSW/RaBitQ/DiskANN/IVF | 需原生 wheel | 主候选 |
| Tantivy（tantivy-py） | Rust + Python | BM25 倒排 | 无（需外接） | 需原生 wheel | 纯 BM25 上界 |
| LanceDB | Rust + Python | 有限 | IVF-PQ / 暴力 | 需原生依赖 | 列存 + 向量候选 |
| Qdrant | 独立服务（可本地） | 支持 | HNSW | 需 sidecar 进程 | 只在服务形态可行时评估 |

> Tantivy/LanceDB/Qdrant 的许可证、版本与 Windows 支持在实验前逐项补录到 `docs/research/README.md` 的事实表；未核实前不写结论。

## 二、数据与题目

- 语料：同一知识库快照（约 60 万 chunk）；额外做 **2 万 / 10 万 / 60 万** 三档子集，观察随规模变化。
- 切块：固定当前 `indexer` 的切块与 `PARSER_SIGNATURE`，不在后端侧二次切块。
- 问句：`data/evals/retrieval_seed.jsonl`（29 curated）+ 自动集（本地 `$SHIYUAN_HOME/evals/retrieval_auto.jsonl`）；报告同时给出 curated 与 auto 两组。
- 标注：沿用「同一事实可接受多个来源文件」的口径；新增 `forbidden_sources` 用于检查错误来源是否被压下去（后续补充）。

## 三、指标

1. 检索质量：hit@1、Recall@5、Recall@10、MRR、无答案准确率（沿用 `retrieval_eval` 口径）。
2. 延迟：冷启动首查、稳态 P50 / P95（每档预热后跑 3 轮取中位数）。
3. 资源：索引磁盘体积、构建耗时、构建峰值内存、查询峰值 RSS。
4. 运维：增量更新（新增/修改/删除各 1,000 文件）耗时与正确性；崩溃恢复；单文件备份可行性。
5. Windows：能否随现有 onedir/NSIS 分发；是否需要额外 VC++ 运行库；冷启动额外耗时。

## 四、实验步骤

1. 固定 commit / wheel 版本，记录到报告头部（禁止「最新版」）。
2. 导出统一输入：`chunk_id, asset_id, text, path, page, sheet, bbox` → JSONL。
3. 各后端按各自最佳实践建索引；分词尽量对齐（中文 Jieba vs trigram 的差异必须单独注明）。
4. 用同一 `benchmarks.retrieval_eval` 逻辑（或等价脚本）跑题，输出统一 JSON。
5. 每档数据重复 3 次，记录中位数与离散度；异常值保留原始日志。
6. 结论只回答三个问题：是否值得迁移、迁移的触发条件、迁移的主要风险。

## 五、决策门槛（先定后测，避免事后找理由）

- 迁移候选必须同时满足：
  1. 稳态 P95 比现有方案低 **≥ 40%**；
  2. curated 集 R@10 不低于现有 **-1 pt**，且 hit@1 有提升；
  3. Windows 单进程分发可行，安装包增量 **≤ 40 MB**；
  4. 增量删除后 24h 内检索不到已删内容（与 P0-1 的失效语义一致）。
- 任一不满足：保留 SQLite FTS5，只吸收查询语义与数据结构设计（如 RRF k=60、过滤下推、BitPacked 只读布局）。

## 六、风险与混淆因素

- 分词差异会同时影响召回与延迟，必须把「分词」和「索引结构」的贡献分开（至少做一次同分词对照）。
- ANN 召回率不是 100%，比较时必须同时报告 Recall@10 与延迟，不能只比 QPS。
- 厂商 benchmark 的数据集（BEIR/Quora）与本项目语料分布差异大，不能直接引用其倍数。
- 向量模型不同会让「向量通道」不可比；实验固定同一模型与同一向量文件。

## 七、交付物

- `data/evals/reports/storage_<backend>_<scale>.json`（本地，不入库）。
- 一页结论：迁移 / 不迁移、触发条件、风险清单。
- 若迁移：单独开分支与回滚路径，不在本设计阶段改产品默认链路。

## 九、结论与决策

**不迁移，继续使用 SQLite FTS5 + 自建向量矩阵。**

- SQLite 在同语料上召回最高（59 万 R@10 0.631），且零额外依赖、单文件可备份。
- Tantivy 延迟与体积优势明确（P50 2.7 ms、370 MB，均约为 SQLite 的 1/4），但 R@10 低 9 pt；
  本轮用 ngram(2,3) 近似中文，未接 jieba，也没有路径/家族通道，不满足预设「R@10 不降 1 pt」门槛。
  保留为「极致延迟/体积」备选，若后续接 jieba 分析器可复测。
- LanceDB 的构建（49 s）与体积（662 MB）都优于 FTS5，但 R@10 低 6.5 pt，P50 约 21 倍（269.5 ms）、
  P95 1.4 s，不满足桌面检索延迟预算；0.41 的原生 FTS 也不支持不带 position 的短语查询。
- Zvec 在 10 万规模召回最好，但构建 277 s、索引 2.3 GB；按线性外推 60 万约 28 min / 14 GB，
  超出桌面端首次建库与安装包预算，不满足「安装包增量 ≤ 40 MB」门槛。
- Qdrant 未评估：需要独立 sidecar 进程，与当前单文件、可离线备份的桌面形态冲突；
  在 FTS5 召回/延迟仍最优且 LanceDB 也未达标的情况下，本轮不构成「必要」条件。
- 未完成的门槛：增量删除、并发读写、崩溃恢复均未测，因此任何迁移都还不具备放行条件。

同时补 Zvec 的增量删除与恢复测试，再决定是否需要第二份候选实现。
